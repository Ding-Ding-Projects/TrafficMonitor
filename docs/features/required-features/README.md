# Complete required-feature applicability inventory

All **110 indexed requirements** are retained here, with independent applicability for the native monitoring application, hosted documentation, portable documentation companion, portable build companion and repository. Extension, game and instruction-source boundaries have exact reasons. An absent future required surface is unfinished, not exempt because it has not been built.

This is a planning and missing-proof record. It claims no implementation acceptance. Stage1 installer evidence cannot establish the interface conversion, complete localization, universal tools or unrelated runtime behavior. Every applicable item requires its own implementation, documentation, localized copy, state ownership, semantic tests, negative omission regression, built interaction and genuine evidence.

## Bounded verified baseline

The source baseline is `47ace8a91966c818d9180ae4a3a0b1c6790eb4c2`. Stage1 records genuine Squirrel callbacks, app-local CRT/MFC loads, stable startup launch, update preservation of configuration and disabled startup, supported uninstall preservation of data and removal of owned startup, and reinstallation. The 1.0.4 receipt records a hidden main window and a visible live traffic monitor attached beneath Explorer's `Shell_TrayWnd`. See [handoff](../../../HANDOFF.md), [1.0.3 receipt](../../../evidence/installer/1.0.3/runtime.json) and [1.0.4 receipt](../../../evidence/installer/1.0.4/runtime.json).

Subsequent sign-in, Explorer restart, fresh-host acquisition and cancellation are not verified. Existing monitoring/settings/plugin code is preserved baseline behavior, not full required-feature proof. Future interface evidence must bind to its actual new build, never relabel Stage1 images.

## Status and evidence schema

`UNFINISHED` means applicable behavior or required proof remains. `PARTIAL` means bounded baseline evidence exists but acceptance remains unfinished. `NOT_APPLICABLE` requires the exact scope reason, reconsidered whenever the product adds the triggering workflow or changes visibility. Runtime surface statuses remain independent, including companion Settings and documentation controls.

[inventory.json](inventory.json) provides public stable IDs, `surfaces`, `implementationDestinations`, `dependsOn` and eight `proof` dimensions, each with a status, expected result and evidence list. All feature articles here are specification drafts; complete Cantonese counterparts and runtime localization remain unfinished. No private instruction-source links, dictionary or operational mapping is shipped.

[Implementation phases](implementation-plan.md) describe native boundaries and dependencies. [Acceptance procedure](acceptance.md) states the still-required checks. No inventory row supplies completion by itself.
