# Workspace responsiveness diagnostics

The preserved workspace candidate is not accepted: candidate 1.0.9043 stopped responding after applying bilingual text and dark appearance. The diagnostic checkpoint adds measurement only, with no claimed repair or runtime result.

Create an empty `<executable>.ui-diagnostics` marker beside an isolated portable executable before launching it to enable a process-local, numeric shared-memory mapping. Without the marker, diagnostic calls cache the disabled state. The mapping closes when the process exits and contains no adapter names, addresses, settings text, search input or persistent user data. Do not enable it in distributed packages.

Schema 2 counts preference Apply/publication, successful posted notifications, accepted Workspace and Settings receipts, theme/settings messages for both owners, row/detail refreshes, layout attempts, chart drawing, row measurement and frame appearance. Each operation records calls, active depth, inclusive timing, maximum duration, latest entry and maximum depth. Reads are not transactional: use repeated timestamped snapshots alongside actual list counts and an independent response probe. A single relationship between changing fields is not a causal verdict.

The first run must distinguish a sustained appearance-message cycle from finite repeated list measurement. Record a blocked UI-thread stack or wait chain if neither pattern explains the stall. Preserve preference-generation checks, conflict handling, high-contrast changes, selection, scroll position and original monitoring behavior.

Build through the root entrypoints against an exact source revision. Before any interaction, record the actual installation, startup, configuration and traffic-history baseline. Resolve controls by stable identity across localization, use search control 52008 and explicit selection indexes, and wait for observable results. Close only an identified owned fixture through the supported lifecycle route; a PID-only termination is not acceptable verification.
