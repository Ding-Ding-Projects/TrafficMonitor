# P1 implementation specification and review amendments

This document resolves the first design review. Where the initial overview or illustrative drawing is less specific, these P1 decisions govern. All behavior below is proposed, not implemented or runtime-verified.

## First-open setup is part of P1

P1 includes `CSetupFlow`, not a future-only route. It starts only after an explicit Open dashboard action when `dashboard.setup.schemaVersion=1` is not complete. Login launch continues collecting with no setup interruption. Existing configuration is loaded as the draft; defaults never replace a saved choice.

Steps: (1) language and message-style disclosure, with the three language modes and two independent funny levels; (2) choose Automatic, All eligible adapters, or one actual adapter; (3) review the existing taskbar and startup states, each with **Keep current** selected initially and explicit change controls; (4) review and Apply. Back retains the draft. Optional changes can be skipped. Save and close persists only the bounded non-sensitive draft and step, with no side effects. Next on the review step becomes Apply, guarded against reentry.

Apply executes independently tracked adapter, taskbar and startup operations on the UI thread through their actual consumers. Each operation records not-started/applying/applied/failed and reads back effective state. An operation already applied is not repeated after restart. If one fails, retain successful effects, identify the failed operation, offer Retry or Keep current and return to review. Never claim rollback that did not occur. Completion is stored only after all required selected operations have verified outcomes; then open Network. A resumed draft rechecks adapter presence and current startup/taskbar state before Apply. A removed chosen adapter requires a new choice. Cancel never enables startup. Setup can be reopened from the real tray/dashboard menu.

The P1 title bar, setup, dashboard, chooser and details all use registered native components. Existing Settings/History/Plugins routes remain actual legacy consumers during staged conversion, visibly described as existing windows, not disabled future tabs. The P1 strip offers only Network plus explicit working entries for existing History, Plugins and Settings; selecting them opens or focuses those existing windows. Do not draw Sensors or Tools navigation as if P1 has implemented it. New tab only lists real destinations that have consumers; the full future destination inventory remains in the design, with its pending rows, outside the shipping interface.

## Complete P1 component and surface closure

P1 requires `surface.window`, `surface.panel`, `text.label`, filled/tonal/text/icon buttons, `input.outlined`, checkbox/switch, navigation tabs, list/table, menu/picker, status chip, metric, chart, sheet/dialog, snackbar/notification history, guidance info and operation progress. Setup uses a step indicator composed of semantic text and selection state. The exact corresponding UIA patterns from components.md are required for every visible instance, including chart equivalent table, adapter selection, menu search, clear controls and dialog actions. The metrics-only subset in the original overview is not the P1 closure.

P1 adapter chooser is a real native sheet with Automatic/All/One mode controls, an actual discovered adapter table, stable selection, local plain-text search, adjacent independent full regex workbench, clear, Apply and Cancel. Its complete regex capability/topic ledger and engine/version-bound implementation are a P1 criterion, not an inert button or a deferred implied feature. A disabled unsupported engine capability is an honest gap, never parity completion. The dashboard table and every contextual/picker menu also have their own field-bound searches. Scope and cost are explicit: P1 is not complete until these applicable controls and their proof exist.

Existing window links are commands, not new shell implementations. `ID_TRAFFIC_HISTORY`, `ID_PLUGIN_MANAGE`, `ID_OPTIONS`, `ID_OPTIONS2`, `ID_APP_ABOUT` and `ID_NETWORK_INFO` retain actual consumers. P1 adds named command descriptors for Open dashboard, Resume setup, Open adapter chooser, Open adapter details, Pause/resume display and Export displayed data. Display pause freezes only that view snapshot; its label and timestamp remain visible and all collection/history continue. Export names the view time and selected scope and uses actual records.

## Stable network identities and observed data

Source inspection finds that `NetWorkConection::index` is an array position into `MIB_IFTABLE`, descriptions are used for matching/persistence, and `theApp.m_in_speed`/`m_out_speed` are selected aggregate rates. P1 must not copy those aggregate rates into every adapter row or pretend the existing vector index is a persistent identity.

Add a separate observational dashboard sampler using `GetIfTable2`/`MIB_IF_ROW2`, with one row per `InterfaceGuid` and `InterfaceLuid`. Use GUID as persisted UI selection identity, LUID plus current discovery epoch as runtime mapping, and `InterfaceIndex` only for joining the current native table. Acquire addresses through `GetAdaptersAddresses`, joining by LUID or validated current interface index, never by display text. Free each API allocation through its matching API. API failure is a reported unavailable snapshot; it is not an empty successful table. If identity conversion is unavailable, show an unavailable identity reason and do not persist an index as if stable.

For each runtime identity maintain previous 64-bit `InOctets`, `OutOctets`, monotonic acquisition timestamp, operational state and sample epoch. A valid rate is `(current - previous) / monotonic_elapsed_seconds`, computed without overflowing intermediate multiplication. First observation is **Collecting first sample**, not zero. Counter decrease, identity/epoch change, nonpositive interval or reconnect resets the baseline and displays **Collecting first sample**. A real unchanged counter over a positive valid interval yields zero. Disconnected rows display **Disconnected** and no throughput; stale data preserves last acquisition time with **Stale**. Removal deletes the live row but retains the open details identity as **Adapter no longer present**, with Refresh and Close. Reorder never changes selection or redirects an open details sheet. Reappearance starts a new sample epoch. Do not infer physical totals by summing duplicate/virtual interfaces or claim the all-interface total equals internet throughput.

Top metric tiles are explicitly **Current monitor scope** and display the existing aggregate values and selected scope. Per-adapter table rates come only from the new observational sampler. Their source/interval can differ and the details explains this. Neither the dashboard sampler nor chart pause writes `m_last_in_bytes`, `m_last_out_bytes`, `m_history_traffic` or daily accounting. Sampling updates coalesce and post immutable snapshots to the dashboard. Add tests proving row rates cannot accidentally bind to the aggregate field.

## Applying adapter selection without changing history

The selection command is a UI-thread transaction with the expected discovery epoch and selected GUID. Before applying, refresh and resolve GUID to current LUID/index, then map to the existing connection using the actual `MIB_IFROW.dwIndex` behind its current array position. Never map a GUID to a vector position cached when the menu opened. No unique mapping means **Adapter changed; refresh and choose again**, no mutation.

Automatic maps to the existing `ID_SELETE_CONNECTION` semantics; All maps to `ID_SELECT_ALL_CONNECTION` with the existing eligibility restriction; One maps to the current `ID_SELECT_ALL_CONNECTION + i + 1` consumer only after revalidation. Prefer extracting these existing bodies into one typed selection consumer called by both old menus and new descriptors, rather than sending a stale numeric command. Preserve `m_connection_name`, `m_connection_name_preferd`, `m_auto_select`, `m_select_all`, `m_connection_change_flag` and existing SaveConfig behavior, adding a persistence readback for All if required. Persist a separate GUID preference additively, never reinterpret or delete historical description-based settings. Do not reset counters or stored daily history; allow the existing change flag to invalidate the transition interval. After application, publish the effective mode and resolved identity; when auto-selection changes, update the visible scope truthfully.

Taskbar setup changes use the existing `OnShowTaskBarWnd` consumer only if the desired value differs from the current state; a toggle command is not an idempotent setter. Startup uses the application-level `CTrafficMonitorApp::GetAutoRun` and `SetAutoRun` consumers, never calls the legacy task helpers directly. Installed mode dispatches through the managed `InstallerLifecycle` path and its owned stable `Update.exe` registration; portable mode retains its existing mechanism. Read back the exact effective registration and enabled/disabled state after every requested change, preserving an existing disabled preference and all unrelated registrations. No elevation consent is automated, no unrelated startup entry is touched, and a declined operation remains failed/incomplete. Existing upgrade/uninstall and portable behavior are regression requirements.

## Searchable Material contextual menus

Every owned right-click menu is a native registered Material menu, including tray, taskbar, metric, chart, adapter row, empty pane, tab/group, picker, settings, appearance, notifications and plugin-management menus. Legacy resource command IDs remain wiring inputs, not permission to retain a visually unconverted popup. Inventory dynamic plugin commands separately; plugin-owned external options windows remain external and are never falsely classified as converted.

Each menu opens with a named clearable plain-text search field and adjacent full regex workbench. Each menu instance and nested submenu owns independent query/pattern/flags/mode/validation/history/snippets. State is scoped by menu context and target identity, never reused against a different adapter or plugin. The workbench stays anchored to that exact field; a constrained menu expands into a bounded sheet retaining origin and focus return.

Search filters command labels and descriptions within the current menu. Nested matches retain their parent path and appear as accessible results with breadcrumb context; entering a submenu preserves the parent's filter and gives the child its own field. A filtered command invokes the same descriptor after current target/enabled/lock validation. No duplicate invocation, stale numeric index, reordered destructive meaning or hidden shortcut activation is permitted. Shortcuts are displayed from actual registered bindings. Destructive commands remain explicit and keep their confirmation flow.

Keyboard: filter initially focused, Tab reaches clear/builder/results, Down/Up navigate remaining items, Enter invokes or opens child, Right opens child, Left returns to parent. Escape first closes the workbench if open; otherwise clears a nonempty filter; otherwise closes the current submenu; final Escape closes root and restores origin focus. Empty results display localized **No matching commands** and a Clear action. Invalid regex retains input, shows the actual validation message, disables result activation and announces invalid state; it never silently changes to plain text or executes old results. Result count is announced after debounced changes; focus does not jump to a different command as results shrink. Every state is covered in English, Cantonese and bilingual modes, both themes and all scales.
