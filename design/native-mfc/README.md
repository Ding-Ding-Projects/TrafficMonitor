# Native monitoring workspace design

Status: design handoff, not implemented or runtime-verified. Baseline: `47ace8a91966c818d9180ae4a3a0b1c6790eb4c2` (application 1.0.4). All numerical readings in reference drawings are explicitly synthetic design fixtures.

## Decision

Keep C++ and MFC throughout the productive application. Keep the existing monitoring loop, plugin ABI, portable configuration, notification-area identity, and Explorer taskbar integration. Add a reusable native Material Design 3 component layer and a modeless productive dashboard. Do not embed a browser, replace the application with a website, or merely recolor existing dialog controls.

The application remains taskbar-visible and main-window-hidden by default. A normal login launch never opens a dashboard or onboarding window. The tray menu gains **Open dashboard** as its first action. Existing **Show main window** retains the compact floating meter semantics, avoiding a compatibility-breaking reinterpretation of that command. Explicit first dashboard opening resumes setup if incomplete; closing setup returns to taskbar monitoring. Setup completion opens the dashboard. The dashboard close button hides this window; Exit remains an explicit, separately named action.

## First independently releasable surface

Release native component foundation plus **Network dashboard** and its adapter details sheet. This release must have real sampling, real adapter selection, explicit unavailable states, native accessibility, light/dark themes, three language modes, DPI reflow, and preserved taskbar/startup/update behavior. Existing Options, history and plugin dialogs remain reachable and explicitly recorded as pending conversion. This is a staged release, never a claim that the whole redesign or required-feature inventory is complete. Do not ship decorative destinations, inactive actions, invented data or claim disabled placeholders as features.

The first slice must implement `NativeSurface`, `NativeText`, `NativeButton`, `NativeIconButton`, `NativeStatusChip`, `NativeMetricTile`, `NativeNavigationTab`, `NativeDisclosure`, and a bounded adapter-details sheet with semantic field groups. Search is not partially introduced: if an adapter chooser is searchable it ships the full field-bound regex workbench and its exact engine capability ledger in that slice, or remains an explicitly unfinished release criterion. No feature requirement is waived by this staging order.

## Workspace and exact destinations

A custom 48-DIP title area shows the display name, real running version and build/release updated-at timestamp with timezone, Accessibility, Notifications, and native minimize/maximize/close controls. Missing provenance reads **Build date unavailable**. Native resizing, Alt+Space, keyboard system-menu access and standard maximize/snap behavior remain available.

Below it, a left-docked browser-style tab strip starts at 200 DIP. Network is pinned. History, Sensors and Plugins are productive destinations. Settings and Tools are explicit destinations, not marketing cards. Ordinary navigation activates an existing destination; the visible New tab control opens the complete searchable destination catalog and only a deliberate catalog selection creates a utility tab. This application is not repository-oriented: it does not create artificial repository tabs. The strip supports all four docking edges, overflow, pinning, groups, keyboard reordering and the four separately scoped discovery searches. At client widths below 900 DIP the strip becomes a 64-DIP icon rail with accessible names and tooltips; a visible expand action opens the full strip above the workspace without resizing the live data pane.

**Network** contains a page title and real selected-adapter scope, a pair of receive/send metrics with exact units and sample age, a time-range control, a 60-second rate chart, the current adapter table, and contextual details. A paused chart is labelled **Display paused; collection continues**. No control pauses accounting accidentally. Disconnected is different from zero throughput; stale samples retain their last timestamp and an explicit stale label. The adapter table exposes stable adapter identity, connection state, receive/send rates and actions. Adapter names and addresses are user data, excluded from public evidence fixtures.

**History** owns the existing daily/calendar traffic model, switching list/calendar, date range, linear/log scale, daily totals, export and selected-record details. **Sensors** owns availability-aware CPU, memory, GPU, disk and temperature readings with source, unit and age. A missing sensor remains **Unavailable** with a reason, never 0. **Plugins** owns actual plugin inventory, enabled state, details, compatibility and the existing options entry. Third-party plugin-owned windows cannot be silently restyled or represented as conforming: record them separately with owner/version and a visible external-window explanation.

**Settings** uses the same tab component internally: General, Taskbar, Floating meter, Connections, Appearance, Language and reading, Accessibility, Notifications, Automation, Privacy and local data, Updates, and Advanced. Existing settings keep their consumers and persistence semantics. Apply validates a draft and commits atomically; Cancel restores the pre-edit state and records discard where required. Preview-only theme changes restore on cancel. Each setting has explicit default, current value, effect, restart requirement and target-specific optional guidance.

**Tools** opens task-specific native workspaces: File conversion, Local models, Server management, Authenticator, Regex workbench, Local history, and Offline help. Each owns its actual records and operations rather than a generic command textbox. Required tool capabilities are unfinished until their corresponding implementation and evidence exist. Tool destinations use complete native forms, typed controls, job progress, cancellation and recovery.

## Visual direction

Direction A, selected: compact instrumentation, neutral tonal surfaces, restrained teal accent, legible numbers, one continuous working canvas. Direction B, rejected: large dashboard cards and oversized display typography that reduce visible adapters and resemble a promotional page. Direction C, rejected: repainting the existing dialog templates without changing component anatomy, layout or interaction.

Use a 4-DIP spacing base; 24-DIP page padding at normal width, 16 at minimum. Group spacing 24, related controls 8 or 12. Surface radii: 12 for supporting panels, 16 for the chart container, 28 for dialogs; buttons use their registered shape token. Main data typography uses 14/20 body, 12/16 metadata, 22/28 page titles, 32/40 metric numbers and 14/20 medium labels. Numbers use tabular shaping. Text has measured intrinsic height, not fixed resource-dialog heights. Bilingual labels place secondary text beneath primary text and grow the row; they never append two long labels onto one line.

Color is semantic. Light: surface `#F8FAF8`, surface-container `#EDF3F0`, on-surface `#18201D`, outline `#6E7973`, primary `#006B5F`, on-primary `#FFFFFF`, primary-container `#9EF2DF`, on-primary-container `#00201B`. Dark: surface `#101512`, container `#1B2520`, on-surface `#DEE6DF`, outline `#89958D`, primary `#80D5C4`, on-primary `#00382F`, container `#005145`, on-container `#9EF2DF`. These are baseline design tokens, not a claim that arbitrary user-selected colors meet contrast. Text contrast must be measured at implementation; custom colors show a contrast warning and offer an accessible reset. Functional chart series use labels and line patterns as well as color.

Bundle approved fonts at build time with license/source/hash manifests. Prefer a complete Latin UI family and complete Traditional Chinese coverage; use DirectWrite fallback when a selected font lacks glyphs. Installed-font selection is allowed but must never make one machine's font an undocumented packaging requirement. Do not synthesize unavailable variable axes. Native high-contrast mode overrides nonessential tonal decoration while retaining structure and visible focus.

## Architecture boundaries

`CTrafficMonitorDlg` remains the lifetime/sampling owner in the first slice. A new modeless `CMonitorDashboard` receives immutable snapshot messages through an adapter, not pointers into mutable timer state. A snapshot contains monotonic sample sequence, UTC acquisition time, elapsed interval, stable adapter IDs, numeric values, units and validity reasons. Rates remain computed by existing accounting logic. UI formatting and display pause cannot mutate counters. Coalesce posted updates and ignore stale sequence numbers; one pending UI wake prevents message-queue growth.

Proposed modules: `NativeUi/Tokens`, `NativeUi/Render`, `NativeUi/Layout`, `NativeUi/Controls`, `NativeUi/Accessibility`, `NativeUi/Localization`, `NativeUi/Interactions`; `Dashboard/MonitorSnapshotAdapter` and `Dashboard/MonitorDashboard`; `UiServices/Commands`, `UiServices/SettingsDraft`, `UiServices/Notifications`, `UiServices/Help`. Avoid a single mixed paint/input/settings file. Preserve existing resource IDs as command routing aliases until every caller migrates.

Render using Direct2D/DirectWrite through existing graphics support where compatible, with an explicit software-rendering fallback and device-loss recovery. Native edit internals may use a Unicode edit control for IME, selection and text services, but the externally rendered field is a registered component with its own container, label, support/error text, clear affordance and focus state. Retain standard provider semantics only when inspection proves them; custom controls require actual UI Automation providers. Canvas pixels alone never constitute accessible controls.
